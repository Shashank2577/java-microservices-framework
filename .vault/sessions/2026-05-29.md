# Session — 2026-05-29

## Commits

## Decisions made today

- **Bumped Gradle to 8.13** (from 8.10 stated in skills) because 8.10 doesn't support JDK 25, and the dev machine has JDK 25 via Homebrew. JDK 21 still required for the build itself (toolchain).
- **Added Foojay toolchain resolver to settings.gradle.kts** so Gradle can auto-provision Temurin 21 on machines that don't have it. Without this, the framework's `JvmVendorSpec.ADOPTIUM` requirement fails on machines with non-Temurin JDKs.
- **Single source of truth for vault frontmatter schema**: `tools/schemas/vault-note.schema.json`. The Python validator now reads it; the GitHub Action consumes it. No more dual definition.
- **PIT mutation as the real coverage signal** is now demonstrated, not aspirational. 91% mutation score on domain-primitives.

## Findings

- **Gradle's typed `libs` accessor is not available inside `subprojects {}` scope.** Hit this with `libs.versions.java.get()`. Workaround: hardcode in subprojects, document that the catalog is the canonical source. Captured as a finding because it's the kind of thing future Claude will re-discover otherwise.
- **Gradle auto-detects `gradle/libs.versions.toml` as a catalog named `libs`.** Manually calling `versionCatalogs { create("libs") { from(...) } }` in `settings.gradle.kts` causes `Invalid catalog definition: 'from' called more than once`. Fix: remove the manual block.
- **Kotlin DSL converts kebab-case catalog aliases to dot-segments.** `dep-check` becomes `libs.plugins.dep.check`, not `libs.plugins.dep-check`. Same for any other hyphenated alias.
- **Spotless google-java-format uses 2-space indents.** The original Java I wrote used 4. `spotlessApply` reformatted everything.
- **`libs.bundles.spring.test` pulled spring-boot-starter-test into a pure-Java module**, which failed to resolve because the module doesn't apply the Spring dependency-management plugin. Added a `pure-test` bundle (JUnit + AssertJ + Mockito only) for domain-layer modules.

## Meta — caught my own anti-pattern

While working today I started writing a retroactive `decisions/0001-adopt-spring-modulith.md` to "fill out" the vault decisions folder. User caught it correctly: vault notes that document a decision must land in the same commit as the decision, not later. Retroactive vault stuffing is the closed-loop failure mode the framework explicitly guards against (see `java-vault` §5 and `java-human-review-ritual` §1). Removed the file before commit. From here on: vault changes ride with the work that produces them.
